# ADR: Использование Spring Batch для пакетной обработки данных

## Статус
Принято

## Контекст

TradeWare сталкивается с проблемами производительности при обработке больших объёмов данных в пиковые периоды:
- Обработка до 400 000 строк в сутки, в пики нагрузка увеличивается в 2-3 раза
- Построчная обработка перегружает транзакционные ресурсы БД
- Отсутствие механизмов retry при ошибках
- Невозможность масштабирования под нагрузкой
- Проблемы с мониторингом и отслеживанием процесса обработки

Текущая система обрабатывает данные об остатках товаров через:
1. Валидацию CSV-файлов
2. Обновление данных из справочников
3. Сохранение в БД

Требования:
- Обработка 100-150 параллельных загрузок в пиковые часы
- Время обработки отчёта на 2000 строк - до 30 секунд
- Готовность к миграции в микросервисную архитектуру
- Централизованный сбор логов и метрик

## Рассмотренные варианты

### 1. Spring Batch ✅
**Плюсы:**
- Проверенное решение для больших объёмов данных
- Встроенная поддержка транзакций и chunk-обработки
- Автоматический retry и skip механизмы
- Мониторинг через JobRepository (метаданные о выполнении)
- Легко интегрируется с существующей Java-инфраструктурой
- Поддержка различных источников данных (CSV, XML, БД, JMS)
- Может работать как standalone или в микросервисе

**Минусы:**
- Требует знания Spring экосистемы
- Overhead для простых задач
- Сложнее горизонтально масштабировать (нужны дополнительные инструменты)

### 2. Apache Airflow
**Плюсы:**
- Гибкое управление сложными DAG
- Хороший UI для мониторинга
- Широкие возможности интеграции

**Минусы:**
- Python-based, не подходит для Java-команды
- Требует отдельной инфраструктуры
- Больше подходит для оркестрации, чем для обработки данных

### 3. Простой многопоточный Java-код
**Плюсы:**
- Максимальная простота
- Полный контроль

**Минусы:**
- Нет встроенного мониторинга
- Нужно самостоятельно реализовывать retry, транзакции, checkpoint
- Сложнее тестировать
- Больше времени на разработку

## Решение

Выбран **Spring Batch** по следующим причинам:

1. **Команда уже знает Java и Spring** - минимальные затраты на обучение
2. **Встроенные возможности для ETL:**
   - ItemReader для чтения CSV
   - ItemProcessor для трансформации (обновление из справочников лояльности)
   - ItemWriter для batch-записи в БД
3. **Chunk-based обработка** - снижает нагрузку на БД через batch-вставки
4. **Автоматический мониторинг** через JobRepository - история выполнения, статусы, ошибки
5. **Готовность к микросервисам** - Spring Batch легко запускается в Spring Boot приложении
6. **Простота для студенческого проекта** - понятная концепция Job → Step → Reader/Processor/Writer

## Архитектура решения

### Компоненты Spring Batch:

**Job: importProductJob**
- Один Step для ETL
- JobCompletionNotificationListener для логирования результатов

**Step: step1**
- Chunk size = 3 (для демонстрации, в проде можно 100-1000)
- Reader → Processor → Writer

**Reader (FlatFileItemReader)**
- Читает product-data.csv
- Парсит поля: productId, productSku, productName, productAmount, productData

**Processor (ProductItemProcessor)**
- Обогащает данные из таблицы loyality_data
- Обновляет productData значением loyalityData по productSku

**Writer (JdbcBatchItemWriter)**
- Batch-вставка в таблицу products
- SQL: INSERT INTO products (...)

**База данных:**
- PostgreSQL с таблицами products и loyality_data
- Таблицы Spring Batch метаданных (BATCH_*)

## Последствия

### Положительные:
- ✅ Обработка данных порциями (chunks) снижает нагрузку на БД
- ✅ Автоматическое логирование через JobRepository
- ✅ Возможность перезапуска failed jobs
- ✅ Простое масштабирование через увеличение chunk size
- ✅ Готовая интеграция с Spring экосистемой
- ✅ Можно добавить multiple steps для сложных pipeline

### Требуют внимания:
- ⚠️ Для параллельных загрузок нужно будет добавить Spring Batch Partitioning или Spring Cloud Data Flow
- ⚠️ Мониторинг можно улучшить через Spring Boot Actuator + Prometheus
- ⚠️ При росте нагрузки рассмотреть async processing или remote chunking
